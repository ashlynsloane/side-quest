# Core Training — Explicit Plan Adjustment Review v1

**Status:** Training-first engineering draft; not deployed to the athlete's installed iPhone. Stacked above source-audit PR #8. No virtual PT, raw pTSS research, automated return-to-training prescription or clinical clearance.

## Product behavior

From **Plan → Preview training-plan changes**, **Weekly Review**, or **Training Baseline Review**, an athlete can inspect an eligible reviewed week and its proposed exercises. The reviewer sees current running-distance, cycling-time, and combined-training-time known subtotals versus previously frozen experimental ceilings.

If the reviewed baseline remains eligible, a numerical overage appears, source overlaps do not require reconciliation, and a pending **Side Quest-generated** endurance session is available, the UI offers two deterministic choices for that session:

1. **Shorten the planned duration by 20%**, rounded down to whole minutes (minimum 10-minute proposed duration), with an explicit before/after comparison.
2. **Defer that generated session**, preserving its original source event and an explicit audit record.

These are *alternatives to inspect*, not recommendations to fill a budget, validated safe doses, a fitted pTSS algorithm, or automatic medical decisions. Reducing time in a run does **not** silently invent a reduction in unmeasured running distance. A preview may remain above the combined ceiling or remain uncertain. Only sessions generated by Side Quest are eligible; imported calendar commitments, manually recorded sessions, actual completed workouts and strength workouts are never edited through this feature.

**Accept** appends a persisted decision and updates the calendar's *effective view*. **Decline** appends a decision without editing the session. **Restore original** appends an undo event and returns the unmodified generated source if baseline, restrictions, source overlap and completion state still permit plan reconsideration.

### Changes survive ordinary plan refreshes

Previously, the Plan tab could regenerate Side Quest's endurance calendar on focus. Directly rewriting the generated event would be fragile. This milestone stores an append-only `training_plan_adjustment_events` table in the **active profile's existing SQLite database**, leaving `training_calendar_events` source records unchanged.

Each event records source event ID, exact source signature, decision, action, adjusted planned minutes and decision time. Calendar reads apply the *latest valid decision* as an overlay. Regenerated calendar data receive that overlay **only when the raw generated event still has an identical signature**; mismatches fail closed to the raw event instead of applying a stale dose to a changed session. A deferred event is hidden from the effective plan, not deleted from the database. The original generated plan can be restored without erasing the historical acceptance event.

### Safety and concurrency

- No candidate without an active, frozen, athlete-attested prior-week baseline; a changed prior week, active clinical constraint or interruption suspends eligibility.
- Candidate generation requires a documented known duration of at least 20 minutes, a still-planned non-completed generated endurance session, a non-past athlete-local date, no unresolved source overlap, and a known arithmetic overage. Completed workouts explicitly supersede their linked plans.
- Before **each click**, reload baseline and proposed exposure, compare a deterministic full-week source signature against the preview, confirm the candidate still exists, then compare the raw generator event signature inside the persisted decision transaction. If any check fails, require a fresh review; no silent best-effort edits.
- A restore rechecks the baseline and clinical state, source overlap, and whether the workout has already been completed. It is not a workaround to increase training during recovery.
- User-visible comparisons report *known subtotals*, unknown run distance/duration, and possible versus unambiguous overages. They do not state medical safety or verified rolling-window compliance.
- Plans from external calendars, PT prescriptions and unrelated athlete data are outside the mutation path.

## Known constraints and release gates

1. No actual-device interaction/persistence/profile-switch test or verified backup/restore yet. No production merge or app build has been issued.
2. Original generator event identity may change with a new training block or plan refresh. Stale overlays intentionally stop applying; the UX needs additional audit diagnostics for outdated accepted decisions.
3. A short-duration option adjusts planned **time** only; not interval structure, hills, intensity, running mileage, workout order or strength programming. The current endurance plan's narrative may still need review after a change.
4. Source completeness is athlete-attested and not provider-audited. Cross-midnight moving-time allocation, unresolved duplicate imports, and incomplete rolling seven-day windows must remain explicitly uncertain.
5. The plan comparison is a **preview of an edited week**, not proof that every weekly and rolling constraint is satisfied. Nothing gets auto-corrected.
6. Saved decisions are app-local and per profile. Sync, migration/restore and cross-device integration are separate engineering tasks.
7. Unit-level logic and typechecking are necessary but not substitutes for end-to-end iPhone QA. Test real generator refresh, accept, force-quit, reopen, decline, restore, activity completed after approval, active injury restriction, and switched athlete profile.

### Next engineering gate

Run an end-to-end on-device test with synthetic training data, then replace unresolved cross-provider duplicates with an explicit manual reconciliation audit and provide a transactionally safe plan-event override persistence/restore test. Only after those checks should the feature become part of the active Side Quest release.
