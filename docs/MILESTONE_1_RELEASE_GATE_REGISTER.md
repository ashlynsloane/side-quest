# Side Quest — Milestone 1 release gate register

**Work branch:** `test/automated-athlete-acceptance-v1`
**Draft review:** [PR #12](https://github.com/ashlynsloane/side-quest/pull/12)
**Status:** DEVELOPMENT ONLY. Do not merge, ship, update the installed iPhone beta,
change a real athlete database or imply medical clearance from a test outcome.

This register distinguishes evidence generated by repeatable tests from evidence
that still requires a real athlete, provider source, or native device.

| Gate | Evidence required | Verified status |
| --- | --- | --- |
| Deterministic planner / synthetic athlete QA | Exact-head TypeScript + full planner test run; reject invalid dose and stale histories | Implemented and exercised in GitHub Actions; re-run on final head |
| SQLite persistence / recovery | Real file-backed preview and decision history, restart, tampering, injected rollback, wrong-owner rejection | Implemented and covered by synthetic tests; not a substitute for real athlete database recovery |
| Read-only review lifecycle | Pending / dismiss / restore, immutable candidate, stale-source detection, bounded inbox, no implicit approval | Implemented in planner and owner-scoped read-only mobile APIs |
| Read-only native navigation and exact exercise diff | Profile/adjustment links to inbox; detail view shows exact station, target and resistance changes and audit history; zero confirm/start actions | Implemented on development branch; mobile TypeScript + iOS JS export verified, physical rendering/interaction **NOT VERIFIED** |
| Mobile SQLite draft integration | Seed a real file-backed synthetic athlete DB and verify mobile read, preview diff, inbox, and no approved workout/decision | Implemented in automated mobile SQLite acceptance; never uses real athlete records |
| Trusted restrictions and exercise execution | Provider/injury restrictions verified from authoritative sources; exact candidate validated in the *same write transaction* that would authorize executable exercise | **NOT IMPLEMENTED.** In-app profile flags and caller-declared coverage are insufficient |
| Real athlete data backup / restore | Explicit export, restore, migration, historical workout reconciliation, cross-profile isolation and rollback on an isolated original-data copy | **NOT VERIFIED.** Synthetic SQLite tests cannot establish this |
| Native device acceptance | Physical iPhone P01–P15, correct isolated app identity, install/launch, cold restart, permissions and UI interactions, crash/recovery behavior | **NOT VERIFIED.** An iOS JavaScript export is not a native launch |
| Release owner authorization | Review and explicit approval of final merge/deployment after all blocking gates pass | **NOT AUTHORIZED** |

## What is implemented (not executable approval)

- Read-only daily training reconciliation, readiness and feedback guidance, and bounded next-session choices.
- An append-only planning-choice journal with current in-app safety rechecks.
- Structural comparison of all reviewed exercise and workout fields; unexpected
  instructions or dose increases fail review.
- Exact-source proposal binding and durable, isolated, unapproved SQLite previews.
- Append-only **preview disposition** events: dismiss and restore-to-pending.
  A restore is not acceptance of the revised exercise prescription.
- Owner-scoped review inbox with stale, dismissed and pending states. Corrupt
  audit rows are surfaced rather than omitted.
- Critical audit-history export and fail-closed transaction rollback on deletion errors.
- Preview creation and review disposition reject impossible calendar dates
  and noncanonical UTC timestamps rather than allowing JavaScript date
  normalization to create misleading audit order. File-backed SQLite tests
  verify those invalid records leave history unchanged.
- Read-only mobile screens at `strength-review-inbox` and `strength-review-detail`,
  reachable through Profile and session adjustment. The inbox loads bounded,
  owner-verified pages of historical drafts, while the detail screen uses one
  owner-scoped service read that combines the exact dose comparison, append-only
  review history and current stale-state assessment. It displays missing or
  changed restrictions as a hold, not a clearance. Late inbox pages from a
  different athlete profile are ignored. No button in either screen writes
  to the approval journal or launches the workout.
- A planner-generated dose summary compares the exact serialized source
  to the full saved candidate. It shows unchanged units, lowered resistance,
  reduced exercise targets, and removed exercises/stations. Any altered
  candidate, modified instruction, or purported executable approval fails closed.
- Native review detail and inbox now require one **consistent, read-only SQLite
  transaction snapshot** for each complete assessment/page. Expo's ordinary
  `withTransactionAsync` can interleave unrelated work, so the native service
  uses `withExclusiveTransactionAsync` and passes its dedicated transaction
  handle to every nested repository query. The callback reader rejects writes
  and nested transactions; missing/unsupported snapshot support fails closed.
  This is a review-display safety gate, **not** executable approval.
- File-backed concurrency tests use a synthetic `BEGIN IMMEDIATE`
  transaction and attempt a competing PT-profile write from another SQLite
  connection. The synthetic writer is rejected while that transaction is held;
  a subsequent review sees the changed restriction after the transaction ends.
  Native Expo transactions use a separate transaction handle, but **native
  writer-blocking behavior has not been verified** and can differ from this
  synthetic immediate transaction. Tests also verify rollback/release of locks
  and that inbox/detail never issue unprotected queries outside the snapshot.
  Mobile SQLite acceptance mocks the native API and rejects unavailable support.
  It also holds an exclusive review read open while requesting an athlete profile
  switch, then verifies the original read finishes before activation of the
  second athlete and that the old athlete cannot be read afterward.
- The exclusive transaction API is native-only; the web review screen must
  report unavailable evidence rather than silently falling back to weaker,
  interleavable transactions. This API is not an iPhone launch test.
- A full mobile-service SQLite test creates an isolated synthetic source block,
  saves a preview, then verifies retrieval, history, read-only inbox and
  preservation of the unchanged original block and empty completion journal.

The only mobile endpoints added for review previews are read-only. The
preview event append methods remain backend-only. No preview status, including
`needs_review`, `pending_review` or `reviewable_preview`, permits exercise
execution or claims clinician authorization.

## Definition of the next implementation gate

A future candidate approval must validate, **inside one athlete-owned
transaction**, at least: exact source block/session, immutable candidate and
binding, fresh athlete intent, current readiness, symptoms, all relevant
provider restrictions, source coverage, no existing incompatible decision,
no completed workout, and an exercise-level dose prescription. It must fail
closed if any source is missing, expired, contradictory or untrusted.

That transaction and corresponding mobile confirmation/undo UI are **not
implemented**. In particular, do not convert a planning-minute cap to sets,
repetitions, resistance or a return-to-running dose by inference.

## Current implementation constraints

- A snapshot string comparison is not a cryptographic attestation. Local
  SQLite profile data does not prove the completeness of outside provider
  restrictions.
- Synthetic CI, JavaScript export and simulator runs never replace physical
  device acceptance or verification against the original athlete data.
- Do not silently progress training based on positive readiness/feedback.
  Changes require explicit athlete authorization; known injury restrictions
  and hard stop limits remain controlling.
